# Multi-Agent Architectural Rules: Orchestration, Handoffs, and Fault Tolerance

This specification establishes production-grade architectural rules and implementation patterns for multi-agent systems (MAS). The directives outlined herein govern state transition logic, state propagation schemas, inter-agent delegation protocols, and deterministic failure recovery mechanisms.

---

## 1. Strict Finite State Machine (FSM) Rules for Agent Orchestration

Agentic systems require explicit control models to prevent runaway loops, unhandled state drifts, and non-deterministic execution paths. Every multi-agent workflow must be formalized as a state machine where execution alternates among well-defined computational modes.

### 1.1 Core Control Grammar and State Primitives

An agentic state machine is governed by five mandatory primitives:

*   **State (`S`)**: A typed, snapshot data structure representing the system's memory at step $t$. It includes the accumulated message history, task-specific intermediate artifacts, routing indicators, and execution metadata.
*   **Event (`E`)**: An input signal generated by an agent decision, a tool completion, an external API callback, or a human interruption.
*   **Guard (`G`)**: A deterministic, auditable boolean predicate $G(S, E) \rightarrow \{0, 1\}$ evaluated prior to any transition. Guards enforce operational bounds, rate limits, and resource quotas.
*   **Action (`A`)**: A procedure executed during a state transition, such as invoking a tool, mutating context keys, writing checkpoints, or formatting model prompts.
*   **Termination (`T`)**: Explicit exit predicates that transition the execution graph to terminal states (`END`), triggered by goal achievement, step limit exhaustion, or explicit stop signals.

```python
from typing import TypedDict, Annotated, List, Literal, Optional
from langchain_core.messages import BaseMessage
from langgraph.graph.message import add_messages

class CoreAgentState(TypedDict):
    messages: Annotated[List[BaseMessage], add_messages]
    working_last: Optional[str]
    retry_count: int
    execution_status: Literal["idle", "planning", "acting", "reflecting", "error", "complete"]
```

### 1.2 FSM Topology and Deterministic State Boundaries

In a standard Finite State Machine (FSM), execution transitions between flat, non-nested state nodes.

1.  **State Boundary Isolation**: Side-effecting tools must run in dedicated `ToolNode` instances distinct from LLM reasoning nodes. LLM nodes evaluate policy $\pi(a_t | c_t)$ to emit intent; tool nodes execute intent deterministically.
2.  **Edge Exclusivity**: Transitions out of an LLM reasoning state must be guarded by conditional routers that inspect the presence of structured tool calls or exit flags in the latest assistant turn.

```python
def route_fsm_step(state: CoreAgentState) -> str:
    last_message = state["messages"][-1]
    tool_calls = getattr(last_message, "tool_calls", None) or []
    if tool_calls:
        return "calling_tool"
    if "FINAL_ANSWER" in getattr(last_message, "content", ""):
        return "finalize"
    return "error"
```

### 1.3 Hierarchical State Machines (HSM): Superstates and Policy Inheritance

When workflows scale beyond simple loops, flat FSMs suffer from transition sprawl. Hierarchical State Machines organize child substates (`PLAN`, `ACT`, `REFLECT`) inside parent superstates (`WORKING`).

*   **Superstate Invariants**: Policies attached to a superstate automatically govern all nested child substates. Global rate limits, recursion caps, and timeout guards are attached at the parent graph level.
*   **Substate Encapsulation**: A subgraph acts as an HSM superstate. Substates execute internal transitions independently and route back to the parent graph only upon reaching the subgraph's internal `END` boundary.

```python
from langgraph.graph import StateGraph, START, END

# Subgraph (Superstate: WORKING)
subgraph_builder = StateGraph(CoreAgentState)

def plan_node(state: CoreAgentState) -> CoreAgentState:
    return {"working_last": "plan"}

def act_node(state: CoreAgentState) -> CoreAgentState:
    return {"working_last": "act"}

subgraph_builder.add_node("PLAN", plan_node)
subgraph_builder.add_node("ACT", act_node)
subgraph_builder.add_edge(START, "PLAN")
subgraph_builder.add_edge("PLAN", "ACT")
subgraph_builder.add_edge("ACT", END)
working_superstate = subgraph_builder.compile()

# Parent Graph
parent_builder = StateGraph(CoreAgentState)
parent_builder.add_node("WORKING", working_superstate)

def global_guard(state: CoreAgentState) -> str:
    if state.get("retry_count", 0) > 5:
        return END
    return "WORKING"

parent_builder.add_edge(START, "WORKING")
parent_builder.add_conditional_edges("WORKING", global_guard, {"WORKING": "WORKING", END: END})
```

### 1.4 Checkpointing, Thread Isolation, and History Markers

Production orchestration requires thread-level state persistence to support resumption, branching, and auditability.

*   **Thread Isolation**: State graphs must execute under explicitly partitioned configuration scopes (`thread_id`), isolating concurrent user sessions.
*   **History Markers**: HSM superstates persist history markers (e.g., `working_last`) inside state checkpoints. Re-entering a superstate reads `working_last` to resume execution at the exact substate prior to interruption or yield.
*   **State Saver Checkpointing**: Memory checkpointers write state deltas after every node execution, enabling replay, rollback, and point-in-time recovery.

## 2. Handoff Protocols and Context Propagation

Multi-agent coordination requires structured standards for passing control, execution state, and data artifacts across agent boundaries.

### 2.1 Shared Bus State Schemas

Agents communicate by reading from and writing to a unified, strongly typed state schema that serves as a state bus.

*   **Schema Overlap Rule**: Overlapping state keys form the shared interface between parent graphs and child agent subgraphs. Keys specific to a specialist agent must be scoped or cleaned prior to upstream handoff.
*   **Message Reducers**: Message sequences must utilize safe appending reducers (`add_messages`) to merge new observations into thread history without overwriting existing messages.

```python
class SwarmState(TypedDict):
    messages: Annotated[List[BaseMessage], add_messages]
    active_agent: str
    task_context: dict
```

### 2.2 Control Flow and State Mutation via Unified Command Primitives

To eliminate detached routing logic, agent nodes can combine state updates and control flow transitions within a single return payload using `Command` primitives.

```python
from langgraph.types import Command

def specialist_agent_node(state: SwarmState) -> Command[Literal["researcher", "writer", "__end__"]]:
    should_transfer = "need_more_data" in state["messages"][-1].content
    if should_transfer:
        return Command(
            goto="researcher",
            update={
                "active_agent": "researcher",
                "task_context": {"query": "Fetch updated metrics"}
            }
        )
    return Command(goto=END, update={"active_agent": "complete"})
```

### 2.3 Supervisor-Worker and Hierarchical Routing Protocols

Centralized agent coordination relies on a supervisor agent that functions as a dynamic router.

1.  **Structured Routing Schema**: The supervisor MUST enforce structured outputs using an explicit schema defining allowable worker nodes (`Literal[*workers, "FINISH"]`).
2.  **Worker Re-Routing**: All worker nodes MUST route control back to the supervisor upon completing their local execution pass, ensuring centralized task evaluation and preventing unmonitored agent-to-agent loops.

```python
from pydantic import BaseModel
from typing import Literal

class SupervisorRouter(BaseModel):
    next_agent: Literal["inventory_specialist", "shipping_specialist", "FINISH"]
    reasoning: str

def supervisor_node(state: CoreAgentState, llm) -> Command[Literal["inventory_specialist", "shipping_specialist", "__end__"]]:
    structured_llm = llm.with_structured_output(SupervisorRouter)
    decision = structured_llm.invoke(state["messages"])
    
    if decision.next_agent == "FINISH":
        return Command(goto=END)
    return Command(goto=decision.next_agent)
```

### 2.4 Peer-to-Peer Swarm Handoff Tools and Context Filtering

In decentralized swarm architectures, peer agents transfer execution using specialized handoff tools.

*   **Explicit Handoff Signatures**: Handoff tools must explicitly specify the target agent name, the handoff rationale, and targeted payload parameters.
*   **Context Pruning / Filtering**: By default, handoff tools pass the full message history. When transferring to domain-specific workers with narrow context windows, handoff functions must prune irrelevant messages, passing only a targeted summary or filtered message list to optimize prompt efficiency.

```python
def create_handoff_tool(target_agent: str, description: str):
    def handoff(task_summary: str) -> Command:
        """Transfer execution to target agent with focused task summary."""
        tool_message = {
            "role": "tool",
            "content": f"Handed off control to {target_agent}. Summary: {task_summary}"
        }
        return Command(
            goto=target_agent,
            update={"messages": [tool_message]}
        )
    handoff.__name__ = f"transfer_to_{target_agent}"
    handoff.__doc__ = description
    return handoff
```

### 2.5 Distributed Inter-Agent Protocols: A2A, Agent Cards, and RPC

For multi-agent systems operating across process, container, or network boundaries:

*   **Agent Card Discovery**: Remote agent services advertise capabilities using machine-readable descriptors detailing identity, capabilities, and interface schemas.
*   **Structured Transport**: Distributed invocations exchange structured request and response objects via JSON-RPC.
*   **Handshake Protocol**: Initiating clients inspect remote Agent Cards to verify version and capability compatibility before task delegation.

## 3. Fallback, Correction, and Retry Behaviors

Production multi-agent architectures must operate resiliently under model non-determinism, API rate limits, tool execution errors, and malformed inputs.

### 3.1 Deterministic Tool Error Capture and Retries Guard Logic

When a tool call throws an exception or returns an invalid payload, execution must route to a dedicated error recovery loop.

1.  **Error Observation Binding**: Tool execution exceptions must not terminate the runtime. Exceptions are caught, formatted as `ToolMessage` outputs containing error context, and appended to state.
2.  **Retry Budget Predicate**: Transition out of the error state is guarded by a retry budget evaluation ($N_{retries} < N_{max}$). If budget remains, arguments are adjusted; if budget is exhausted, the graph transitions gracefully to terminal failure or human escalation.

```python
def execution_tool_node(state: CoreAgentState) -> dict:
    last_msg = state["messages"][-1]
    tool_call = last_msg.tool_calls[0]
    try:
        result = invoke_external_tool(tool_call["name"], tool_call["args"])
        return {"messages": [ToolMessage(content=str(result), tool_call_id=tool_call["id"])], "retry_count": 0}
    except Exception as err:
        error_msg = f"Tool execution error: {str(err)}. Adjust arguments and retry."
        return {
            "messages": [ToolMessage(content=error_msg, tool_call_id=tool_call["id"])],
            "retry_count": state.get("retry_count", 0) + 1
        }
```

### 3.2 In-Loop Self-Correction: ReAct and Reflexion Paradigms

For complex tasks, agents utilize programmatic self-correction loops before presenting outputs.

*   **ReAct Loop**: Interleaves Thought, Action, and Observation. If an observation reveals an incomplete or erroneous output, the model generates a corrective Thought step.
*   **Reflexion Memory Buffer**: Upon task failure, a dedicated reflection step generates a strategic self-critique answering: *"What misstep occurred and what plan should be followed next?"* This critique is written to a persistent reflection buffer and prepended to the system prompt of the subsequent trial.

```python
def reflection_node(state: CoreAgentState, llm) -> CoreAgentState:
    trial_transcript = format_messages(state["messages"])
    reflection_prompt = f"""
    You attempted the following task and failed:
    {trial_transcript}
    Diagnose the specific strategic error. Output a corrective plan starting with 'Plan:'
    """
    critique = llm.invoke(reflection_prompt).content
    return {"messages": [BaseMessage(content=f"Prior Reflection Plan: {critique}", type="system")]}
```

### 3.3 Guardrail Validation and Recovery Modes

Input and output guardrails evaluate model generations against formatting and structural criteria. Upon validation failure, guardrails execute one of six standardized recovery protocols:

| Recovery Mode | Operational Mechanism |
| :--- | :--- |
| **Re-ask** | Prompts the LLM to re-generate the output with explicit instructions highlighting the failed validation rule. |
| **Fix** | Programmatically mutates or repairs the invalid payload without re-querying the LLM. |
| **Filter** | Strips only the invalid attributes from the output structure, passing valid attributes downstream. |
| **Refrain** | Suppresses response generation entirely and emits a standardized notice. |
| **Exception** | Raises a software exception to trigger higher-level system exception handlers or fallback routes. |
| **Fix_Reask** | Applies a programmatic fix first; if secondary validation fails, triggers an LLM re-ask pass. |

### 3.4 Human-in-the-Loop (HITL) Interruption Gates

Critical actions (such as database modifications, financial transactions, or workflow cancellations) require human authorization prior to execution.

1.  **Isolation Invariant**: Side-effecting operations MUST NOT exist in the same graph node as the `interrupt()` prompt. The graph MUST pause first via `interrupt()`, collect explicit approval, and perform side effects in a downstream node.
2.  **Interrupt Actions**: Approval gates must accept structured human responses enforcing three allowed actions: `accept` (execute as proposed), `edit` (modify parameters and re-evaluate gate), or `reject` (cancel operation and append explanation).

```python
from langgraph.types import interrupt

def hitl_approval_gate(state: CoreAgentState) -> Command[Literal["execute_action", "propose_action"]]:
    proposed_action = state["proposed_action"]
    
    # Execution pauses here; state is checkpointed
    human_decision = interrupt({
        "task": "Approve sensitive operation",
        "proposed_action": proposed_action,
        "allowed_actions": ["approve", "edit", "reject"]
    })
    
    action = human_decision.get("action")
    if action == "approve":
        return Command(goto="execute_action")
    elif action == "edit":
        updated_params = human_decision.get("updated_params", {})
        proposed_action["args"].update(updated_params)
        return Command(goto="hitl_approval_gate", update={"proposed_action": proposed_action})
    else:
        return Command(goto=END, update={"execution_status": "rejected"})
```

### 3.5 Circuit Breakers, Execution Caps, and Fallback Cascades

To safeguard system stability against infinite agent loops and cascade failures:

*   **Recursion Limits**: All graph execution runs must enforce explicit recursion caps (`recursion_limit=50`). Reaching the cap triggers a fallback handler.
*   **Circuit Breakers**: If a tool or specialist agent fails repeatedly across $N$ consecutive attempts, the router trips a circuit breaker, routing subsequent calls to a degraded secondary fallback model or human operator queue.
*   **Fallback Cascades**: When primary high-capacity models experience rate limits or API downtime, orchestration automatically fails over to local or lower-tier models to execute remaining deterministic tasks.
